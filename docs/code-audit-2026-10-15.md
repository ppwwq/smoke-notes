## 后续修复：审查中列出的四项确认问题

### 已修复 P1：桌面退出绕过编辑器保存

原先在自动保存延迟内点击托盘“退出”，或在 IME 组合输入期间退出，可丢失内存草稿。现在主进程向主窗口和全部便签窗口发出带编号的保存请求，全部确认后才保存窗口状态并退出。

renderer 等待组合输入和笔记保存完成，同步锁定界面并再次检查保存后才确认。保存失败、30 秒超时、窗口状态写入失败、页面重新载入或窗口正在切换时均取消退出；取消会解锁全部窗口，旧请求的迟到确认不再有效。等待期间禁止发起新的窗口切换、打开或关闭。测试覆盖真实编辑器、本地主窗口打包代码与保存协调器；尚未在 Windows 托盘实测，不涵盖系统强杀或其他非笔记表单草稿。

### 已修复 P1：切换到已有窗口会直接销毁目标草稿

原先从 A 的侧签切换到已打开的 B 时，会导航 A 并销毁原 B，丢失 B 的内存草稿。现在直接聚焦 B，保留 A、B 两个窗口、各自草稿和编辑状态。目标仍在创建时先等待创建完成；未打开的目标仍复用源窗口。

窗口管理器及主进程 IPC 回归验证两个窗口均未导航或销毁，窗口身份和关闭行为正确。

### 已修复 P2：历史配对码碰撞会使新旧配对码都不可用

新增 `rotate_pairing_code` RPC，在同一事务内插入新码并作废旧码，按工作区串行化，验证调用者成员身份并由服务器设置五分钟有效期。保留历史码唯一约束；边缘函数遇到唯一键碰撞会重新生成，最多尝试十次，其他错误立即返回。

真实 PostgreSQL 验证碰撞失败后旧码仍可兑换、作废步骤失败后完整回滚、六个并发轮换最终只保留一个有效码，以及匿名/跨工作区请求被拒绝。辅助函数测试验证碰撞重试、重试上限和错误响应处理。

### 已修复 P2：并发首次创建工作区会分流

`bootstrap_workspace` 在查询或创建前取得用户级事务锁，与配对兑换使用相同的用户锁。真实 PostgreSQL 测试强制六个首次调用同时等待锁，释放后均返回相同工作区 ID，只创建一条成员关系；已有成员重用原空间，缺少身份或匿名调用被拒绝。

## 设计边界与未完成验证

- 真实的 notebook/todo 同字段版本冲突仍采用服务器记录，可能覆盖本地后续编辑；尚未扩展为便签式三方合并。
- Web Locks 不可用时仅提供当前 JS 进程内串行化，不能把它描述为完整跨标签锁。
- 普通删除、完成待办、设置中恢复等部分异步操作尚未统一失败提示/重复操作保护。
- 静态观察还包括未调用的回收站清理存在读后恢复竞争、富文本嵌套节点缺少完整结构验证、极密排序值缺少自动重排；本轮不将这些观察计入已复现修复。
- IME 自动回归使用合成事件；没有验证真实 Windows/iOS 输入法、实体设备、线上双向同步、托盘退出或实际 Cloudflare 发布。

## 服务端验证与发布顺序

`supabase/tests/database/test_mutation.py` 在无网络、无公开端口的临时 PostgreSQL 17 中应用全部迁移并验证事务、并发、回滚、角色和工作区权限。它不替代托管 Supabase Auth、PostgREST、边缘函数和 Realtime 的端到端验证，也没有执行单独的 pgTAP `rls.test.sql`。

服务端修复必须先应用 `202610150001_atomic_mutations.sql` 和 `202610150002_atomic_pairing_and_bootstrap.sql`，再部署 `apply-mutation`、`create-pairing` 函数。仅发布网页不会启用这些服务端修复；桌面退出和窗口切换修复需要新版桌面应用。详见 [数据库验证说明](../supabase/tests/database/README.md)。
